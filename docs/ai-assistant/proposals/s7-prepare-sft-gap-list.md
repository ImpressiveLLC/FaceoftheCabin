## 1. What a dry run is for

The path in HO-2026-10-25 is: S6 freeze, then an S7 dry run of `prepare_sft.py` that produces splits and a data card with nothing exported or trained. A dry run is useful only if it can fail for the right reasons: a leaked row, an unreviewed row, a row that cannot be labeled. Today it would pass or fail for several wrong ones (section 3).

## 2. What the tool does today

`split_rows(rows, gold)` takes reviewed rows and dev gold. It refuses a row unless `provenance.review_status == "approved"` with reviewer, reviewed_at, source, revision, sha256 and license present, and for an agent label it checks `audit_result` (`check_agent_audit`, a passed audit by 90 percent or better, a linked cohort and audit-sample hash, the row hash unchanged since the audit, audited sample size at least 10 percent of the cohort). It drops nothing silently: an empty, duplicate, gold-text or gold-group row raises. It validates the target against the contract (with `card_target`) and vocabulary, then assigns a split by `sha256(group) % 10` (0 is "test", 1 is "validation", rest "train") and raises if any split is empty. It prints only counts.

## 4. Manifests for the auditor and for the dry run: two stages

Codex's preparation checklist (7025518467) needs a train-only manifest and hash, provenance, author and labeler identities, and a precommitted reproducible sample with its denominators before any scoring. `prepare_sft.py` accepts only approved, audit-passed rows, so the manifest the auditor needs must exist **before** `split_rows` can run. The lifecycle therefore has four stages and two manifests; the field names reuse what the importer already writes (`audit.manifest.json`, `audit_result`) so nothing new has to be learned. Both are **private**; only counts and hashes go to the hub.

Stages: **(1)** bind families, label, import to an agreed cohort; **(2)** precommitted blind-audit manifest; **(3)** independent audit and promotion (`record-audit`); **(4)** S6 freeze, then the S7 training manifest and splits.

### 4.1 Pre-audit cohort manifest (stage 2, `cohort-manifest.json`)

- `manifest_version`, `built_at`, `manifest_id` (first 12 hex of the sha256 of the canonical payload without derived fields, so it never hashes itself), `stage: "pre-audit"`.
- `tool`: git commit and sha256 of `grading/review_packets.py`, `grading/bind_families.py`, `grading/s1_sample.py`, `contract.py`, `vocabulary.py`.
- `inputs`: sha256 of the sample or exported-and-bound candidate file, the family maps, the packet manifest, the label files' hashes (not their content), and the labelers' ids and models.
- `cohort`: `track`, `cohort_sha256`, `cohort_n`, the versioned row payload version (G6), `audit_share` (0.10 for A, 0.20 for B), `audit_n`, `seed`, `audit_ids_sha256`, `audit_content_sha256`, and the sample selection rule as text, all **precommitted before any audit label exists**.
- `counts` by intent and by source; `families_sha256` (the S1 formula) for the cohort.
- `people_and_agents`: author ids, first and second labeler ids and models, and family authors.
- `auditor`: id, `auditor_kind: agent`, the election reference (6874239053), the label "agent auditor(s) elected by Codex under owner amendment, not human audit", and `conflict_exclusion_sha256` (hash of the sorted family ids the auditor authored, labeled or trained on). **A conflicted family is not dropped from the audit obligation: it is reassigned to a different eligible auditor**, recorded as a second auditor block for that family set, so every cohort row has an audit.
- `result`: `READY_FOR_AUDIT` only if every input hash matches. It makes **no claim** of approval or training readiness and does not require the audit it exists to enable.

### 4.2 Post-audit training manifest (stage 4, `train-manifest.json`)

Written by the S7 dry run only from rows that `record-audit` promoted. It carries everything in 4.1 per track (as references to the cohort manifest ids), plus: `tool` hashes of `prepare_sft.py`; `inputs` including the S1 and S2 family maps, `gold.jsonl` and the S6 `freeze_id` (or `NOT_RUN: S6`, which is a **hold for S7**, not for the earlier train-only audit stage, which proceeds under its own authorization); `counts` of rows and families per split, intent, track and source, plus `quarantined` and `refused_by_training`; `hashes` for `train_ids_sha256` (sorted ids joined by newline, the S1 form), `train_content_sha256` (the versioned row payload of G6, sorted by id), `quarantine_ids_sha256` and `frozen_family_ids_sha256`; and `result: READY_FOR_DRY_RUN` only if every input hash matches and no row failed a check.

The auditor can then check, from stage 2, that its sample is the precommitted one (`seed`, `audit_n`, the ids hash), that the content it is shown hashes to `audit_content_sha256` including the card, and that none of its own families is in its cohort.
