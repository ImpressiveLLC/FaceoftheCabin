# Operating the platform

Audience: operators and maintainers; household instructions must be projected to the appropriate role. Evidence: repository baseline in the [index](../README.md); live behavior not reverified. Maintained jointly through PR review.

## Products and responsibility

Family Hub is the static HTML/JavaScript family experience. Cabin orchestration is the React interface with a Spring Boot backend. Both use platform capabilities, but the assistant must distinguish their user journeys and data ownership. Home Assistant, Node-RED and backend workflows are distinct execution systems; a rule visible in one is not proof it exists in the others. Source: [repository map](../../../README.md), [Family Hub source](../../../family-hub/family-hub.html), [app panels](../../../cabin-orchestration-platform/ui/src/App.jsx), [RulesController](../../../cabin-orchestration-platform/backend/src/main/java/com/cabin/orchestrator/api/RulesController.java).

## Presence and location roles

### What the presence badge means

 The toolbar badge shows where the household is, derived from signals phones publish: a GPS zone enter/leave, or a phone seen on the location's WiFi. It is a display and a severity input, not proof that anyone is or is not there. With no live signal it is a manual setting. Check the signal's source and age before relying on it: once the phone "last seen" heartbeat is in place the badge shows how long ago the phone last reported, and past the limit (6 hours by default) it reads "Presence unknown" instead of Away or At Cabin. A phone that is off Tailscale, or whose Home Assistant Companion app has stopped reporting, makes the signal go stale. Stale means unknown, never away. Sources: [PresenceController](../../../cabin-orchestration-platform/backend/src/main/java/com/cabin/orchestrator/api/PresenceController.java), [PRESENCE.md](../../../cabin-orchestration-platform/infra/cabin-security/homeassistant/PRESENCE.md).

### Who counts: location roles (ratified 2026-10-13, D24)

 Presence counts **primary** users only: the people who live at or actively use the location. A **maintenance** user sets the location up and maintains it without living there. They hold the same credentials as a primary user plus elevated ones, and for presence they are a guest: their phone is not checked, never counts, and the siren gate does not recognize them. One person can hold both roles at one location (at the cabin, Nate does). This is not the same as a signed-in role such as ADMINISTRATOR, which says what someone may do, not whether they count as present; a location role grants or removes no permission. Decided 2026-10-13: a maintenance-only person sets the sirens off unless they disarm first, by design; children count as primary users for the siren gate and appear only as "household member present" on the display.

**What the hub does with roles (corrected 2026-10-31; this section used to say the backend does not know roles).** Since 2026-10-30 (W-38, merged and, per the backlog, deployed; not re-checked for this guide) the hub keeps a list of who holds which role at each location. An administrator sets it in **Config > Location Roles**: each person has **Primary** and **Maintenance** boxes per location, **Assign** adds a person, and **Remove** (with a confirm step) takes them off. Other people see "Admin access required to assign location roles."

- **Maintenance only:** the person's phone signal is not counted as presence. Their arrival is recorded as a maintenance visit in the hub's event history instead. The app has no screen that lists those visits, and a hub restart does not record a false visit.
- **No role:** the person is still counted as present, so nobody silently stops being recognized, and is listed under **Counted but not assigned** with **Make primary** and **Make maintenance** buttons. Removing someone's roles does not stop their signal counting; while their phone reports, they appear on that list again.

What roles in Config do not change: the siren gate in Node-RED and the phone checks in Home Assistant. Those still follow what is configured on the hub, where a phone check exists for primary users only. Assigning a person in Config does not give them a phone check; the Home Assistant files are generated from a reviewed roster and applied on the hub by the owner, and as of 2026-10-30 that host step had not been applied. Source: [D24](../../governance/decisions/ontology-decisions.md#d24--location-roles-primary-and-maintenance), [check_authorized_user_phone_wifi in the ontology](../../ontology.yaml), W-38 and W-129 in [the backlog](../../governance/backlog.md), [LocationRoleService](../../../cabin-orchestration-platform/backend/src/main/java/com/cabin/orchestrator/presence/LocationRoleService.java), [PresenceSignalRegistry](../../../cabin-orchestration-platform/backend/src/main/java/com/cabin/orchestrator/presence/PresenceSignalRegistry.java) (`MAINTENANCE_VISIT`, `unregisteredCounted`), `LocationRolesCard` in [App.jsx](../../../cabin-orchestration-platform/ui/src/App.jsx), [presence generator](../../../cabin-orchestration-platform/infra/cabin-security/homeassistant/gen/README.md).

### Arming

 The hub cannot arm or disarm; arming is done in Home Assistant or Node-RED. When the system is armed while presence shows someone at that location, the hub shows a banner (it warns and never blocks). The siren gate sounds the sirens when a door opens while armed unless it recognizes an authorized user as present. Anyone else who is there, and a lost phone signal, can set it off. Do not tell anyone the system is safe or disarmed from presence alone: check the Armed/Disarmed badge, and disarm before staying. A maintenance-only person on site is a guest to the gate, so the system should be disarmed before they enter. Source: [siren gate in the ontology](../../ontology.yaml), [W-35](../../governance/backlog.md).

### What is not settled

 The phone WiFi check has never matched on the cabin network (cause unconfirmed; a private/randomized phone MAC is the leading suspect). The Home Assistant Companion app is currently the only GPS source and is not meant to be required long term. Both are open design items (W-36, W-37). **The owner's direction (2026-10-04) is that a phone's Tailscale should not be part of presence; it is a remote device for approvals only.** One consequence to state plainly if asked whether the siren will sound while the household is away: with Home Assistant not reachable from the internet, a phone that is away from the location and not on Tailscale cannot report that it left, so GPS only reliably reports arrival. Presence can then stay "home" after everyone leaves, and once the signal is more than 6 hours old the siren gate sends a push notification instead of sounding the siren. So until a departure signal that does not need the phone's Tailscale exists (W-37, W-36), arming while away should be treated as alert-only protection, not as a guaranteed siren. A feature described here counts as live only once its PR is merged and deployed, and for Home Assistant and Node-RED changes only after someone applies it on the hub by hand: the stale-presence siren rule (W-33, PR 118), the badge age (W-34, PR 121), the publishers and heartbeat (W-23, PR 122) and the arming banner (W-35, PR 124). Check which are deployed before stating any of them as current behavior.

## Users and family data

Start with the [user guide's sign-in versus attribution explanation](../../USER_GUIDE.md). Selecting a family profile tells the interface who is writing; it is not an authentication or privilege grant. The server derives household role from verified authentication. The enum includes ADMINISTRATOR, ADULT_HOUSEHOLD_MEMBER, CHILD, KIOSK_DISPLAY and SERVICE, but the enum comment explicitly says some values have no live derivation path yet. Do not promise every listed role can already be enrolled through an existing screen. If a note/profile/chore appears on one device only: preserve the local work, check the other device's sign-in and connection, then verify a real cross-device change. Do not call a server error “no data,” and do not erase the local copy as a first troubleshooting step. Existing sync behavior and troubleshooting are in [USER_GUIDE](../../USER_GUIDE.md); the requested consistent recovery experience is defined in [UX Journey Standard](../../UX_JOURNEY_STANDARD.md). Not all desired recovery UI is implemented.

**Note recovery correction:** copy a local-only note's text privately before signing in again or refreshing. `sendNote()` saves a failed send locally, but `refreshNotesFromServer()` replaces the cache with server notes; the inspected path has no replay queue. The older guide's implication of automatic later upload is not reliable. Check for an existing server copy before deliberately resending, then verify on a second signed-in device. ## Device onboarding

**Short answers.** External platform confirmation registers a CANDIDATE, not an assigned or operating device. It is persisted, so by design the record survives a backend restart, but it stays a candidate until it is accepted and configured; a record existing is not proof the hardware works, and the source shows the design, not an observed restart. Passive-discovery candidates are a separate path and are not persisted by republishing. Import proposals are not an innocuous health probe: `GET /api/platform-import/{platform}/proposals` contacts the provider and upserts import records; read existing records with `GET /api/platform-import/records` (it has its own role check) instead. If a confirmed import is not listed after a restart, first establish whether it came from a platform import or passive discovery, and verify the saved state before re-importing; the cause is unknown until checked.

1. Identify the supported source: existing adapter discovery, device-specific assisted discovery or an external platform import. Review prerequisites and permission before triggering a provider call.
2. Review proposed identity/type/location against the physical device. Keep confirmed `entity_id` stable; display labels are the presentation mechanism.
3. Confirm the import/proposal through its existing flow, then check lifecycle. External platform confirmation registers a **CANDIDATE**, not an assigned/operating device. Acceptance is a separate lifecycle action; configuration/assignment remains explicit.
4. Verify the device's actual telemetry/health and the intended display or rule target. A record existing is not proof the hardware works.

Sources: [DeviceDiscoveryController](../../../cabin-orchestration-platform/backend/src/main/java/com/cabin/orchestrator/api/DeviceDiscoveryController.java), [PlatformImportController](../../../cabin-orchestration-platform/backend/src/main/java/com/cabin/orchestrator/api/PlatformImportController.java), [DeviceController lifecycle](../../../cabin-orchestration-platform/backend/src/main/java/com/cabin/orchestrator/api/DeviceController.java), [DeviceLifecycleState](../../../cabin-orchestration-platform/backend/src/main/java/com/cabin/orchestrator/devices/model/DeviceLifecycleState.java).

Confirming a platform import (`confirm`) registers a CANDIDATE and persists it through `DeviceRegistry.registerPersistentCandidate()` with the `importedFrom` provenance tag, so the candidate survives a backend restart (PR #46, 2026-09-08). Persisted does not mean assigned: the device stays a candidate until it is accepted and configured, so do not represent a successful confirmation as a finished installation. Candidates registered passively from discovery are a separate path and are not persisted by republishing; verify the saved state rather than assuming it. Also, `GET /api/platform-import/{platform}/proposals` contacts the provider and upserts import records; it is not an innocuous health probe. `GET /api/platform-import/records` reads existing records and has its own role check. Source: the controller's `proposals`, `records` and `confirm` methods.

Historical Claude findings now reconciled with source: discovery lookup-result persistence does not persist an undecided candidate; the optional external discovery provider can fall back to local catalog results; and the current Remove action applies IGNORE rather than hard deletion. Do not repeat the older Remove/deployment claims as current behavior. See [recovered evidence H01–H05](../corpus/local-history-evidence.md#findings-reconciled-with-current-source) and [Q04–Q07](../corpus/eval-answer-evidence.md#q04--clearer-names-without-changing-identity).

A persisted device is restored with its lifecycle state when the backend starts (`DeviceRegistry.restorePersistedDevices`, which loads every stored record that has a lifecycle state, Candidates included). In Device Manager the State filter controls which lifecycle states are listed: its default shows Candidates, Available and Assigned, and the selection is remembered in the browser, so confirm Candidates is selected before concluding that a candidate is missing. The other filters are described in [Devices: find a device](devices.md#find-a-device-filters-groups-and-layout); the plain-language device states, add, remove and on/off steps are in [Devices](devices.md).

## An alert keeps firing

Audience: administrator. Rules & Alerts and Monitoring show alerts; when the same alert keeps coming back, or keeps being silenced, the platform opens an **Alert noise** opportunity (Rules & Alerts, Optimization Opportunities) for that device, naming each alert, how many times it was raised and silenced in the last seven days, and what to look at. It is a pattern worth a look, never an automatic change, and it reads the reviewable record in Monitoring, Sensor History, Alert History. That record starts when the log was turned on, so a quiet history for a flaky device can mean "not logged yet".

What to look at depends on the alert:

- **A device missed its check-in.** Compare how often the device really reports with the check-in window on its device page ("Expected within ... min"). If it normally reports less often, the window is too tight and it will keep looking late. If it is sometimes on time and sometimes not, look at its link (signal quality, distance to a router) and its battery.
- **A workflow notification repeats.** The workflow notifies every time its condition recurs. Give its notify action a cooldown; an existing workflow cannot be edited yet, so create the replacement and delete the old one. Also check whether the reading sits right at the trigger threshold, which means the device may need repositioning.
- **A command is not confirmed.** The device did not report the commanded state. Check the device, its link and battery, and whether another automation (Home Assistant, Node-RED) is reverting the command.
- **A built-in presence rule** (motion while unoccupied, lock unlocked) usually means the presence picture is wrong: check the presence signals before the rule.
- **Any other built-in backend rule.** Its threshold is a deploy-time setting, not editable in the app. Check the reading is genuinely near the threshold before asking for a change.
- **An alert silenced three or more times** is telling you something: retune it as above, or retire it. A routinely silenced alert is easy to miss on the day it is real.

**Safety alerts are different.** For a water-leak, smoke or CO device, any device alarm, and the freeze-risk and safety-alarm rules, repeats are a reason to find the cause (sensor placement, a slow leak, a failing battery, a genuinely cold spot, a faulty probe). Silencing is not a fix and this guidance never suggests tuning those down.

## Rules and alerts: trigger and action catalog (K05)

Audience: administrator. Sources: [JdbcWorkflowVocabularyStore](../../../cabin-orchestration-platform/backend/src/main/java/com/cabin/orchestrator/workflow/JdbcWorkflowVocabularyStore.java), [RulesController](../../../cabin-orchestration-platform/backend/src/main/java/com/cabin/orchestrator/api/RulesController.java), [WorkflowActionTargetValidator](../../../cabin-orchestration-platform/backend/src/main/java/com/cabin/orchestrator/workflow/WorkflowActionTargetValidator.java), [WorkflowRuleService](../../../cabin-orchestration-platform/backend/src/main/java/com/cabin/orchestrator/workflow/WorkflowRuleService.java).

**The catalog is code, not a setting.** The supported trigger and action lists live in code and are written to the database on every backend start; no endpoint edits them. `GET /api/rules/vocabulary/triggers` and `/actions` (open reads) return the supported rows plus ontology candidates shown as unsupported; a candidate cannot be run.

**26 supported triggers**, in pairs (detected / cleared) unless noted: water leak, door contact opened/closed, motion, tamper, battery low, device (plug) turned on/off, freeze risk (below 32°F; clears at 36°F or above), mold risk (humidity 60% or above; clears below 58%), Blink camera motion, Kidde CO alarm (pushed through the `cabin/kidde/co_alarm` bridge), armed away / disarmed, someone arrived / departed. Singles: camera detects motion; Home Assistant entity changed (no clear signal; scope it with a trigger device). Tamper and battery apply to any device reporting that field. A trigger with a clear signal keeps its execution active until the condition clears or a person clears it; any other trigger clears its execution as it fires.

**Only 4 supported actions:** `action_main_water_valve_off`, `action_main_water_valve_open` (privileged), `notify_critical`, `log_event` (the event is already stored; this only shows an explicit log step). There is no action for locks, lights, heaters, plugs or thermostats. Create and activate do not reject an action id missing from the catalog; running it records `success: false` ("Unknown actionDefinitionId").

**Checks at create, activate and retarget.** Validation failures come back as an `error` field in the JSON body. (1) A `DEVICE_EVENT` workflow may not contain `action_main_water_valve_open`; reopening is human-only through a `MANUAL` workflow. (2) An action that needs a target must name a device that exists, has the `COMMAND` capability and is `ASSIGNED` (not merely available). Create always saves disabled; `POST .../activate` is separate and repeats both checks; deactivate does not validate. `POST .../actions/{actionId}/retarget` repairs a target and re-validates. `GET /api/rules/workflows` adds a health value (BROKEN, DEGRADED or HEALTHY) from the same checks plus a missed check-in.

**Running.** An action's optional `cooldownSeconds` skips it after a recent success. A valve action is refused unless the target is enabled and `COMMAND`-capable; otherwise the command is published and recorded `ACCEPTED` or `PUBLISH_FAILED`, with a later confirmation check, so `ACCEPTED` is not proof the valve moved. `POST .../fire` works only on an enabled `MANUAL` workflow; every tap is a new execution recorded as `MANUAL:<email>`. Reset mode is `AUTO_ON_CLEAR` or `MANUAL_ONLY`; a person can clear any execution.

**Who can do what.** Reads under `/api/rules` are open. Writes (create, activate, deactivate, delete, fire, retarget, view, clear) need a verified signed-in session; guest links and demo viewers get none. RulesController applies no household-role check of its own, and the actor email comes from the verified token. Home Assistant and Node-RED keep the leak, freeze and siren automations; do not rebuild them here.

## Opportunities and the Tech ID Service (K19)

Audience: administrator. Two separate lists are both shown as opportunities. Neither is evidence that anything was built or fixed.

**Optimization opportunities** ([OpportunitiesController](../../../cabin-orchestration-platform/backend/src/main/java/com/cabin/orchestrator/api/OpportunitiesController.java), `/api/opportunities`, administrator only). Statuses are `OPEN`, `ACKNOWLEDGED` and `RESOLVED`, set only by a person (`PATCH .../status` accepts `ACKNOWLEDGED` or `RESOLVED`, never `OPEN`). Scans (hourly by default) never change a status; they create a row or refresh an `OPEN` or `ACKNOWLEDGED` one. Two types exist (corrected 2026-10-31): `DUPLICATE_READING`, see [Optimization Opportunities](alerts-and-notifications.md#optimization-opportunities-power-and-duplicate-readings), and `POWER_DRAW_ANOMALY`: a `POWER_METER` device whose elapsed time since its last recorded sample at or below 1.0 W (or, if none in the 30-day lookback, since its earliest numeric sample in that window) is at least 48 hours (`OPPORTUNITIES_*` settings, see [configuration](configuration.md)). This recorded-sample heuristic checks no freshness, continuity or current draw, so sparse or stale telemetry can produce or hide a row. It means "worth a look", not "waste": the mechanical-room heater is expected to draw power. A recurring `RESOLVED` condition opens a new row; `RESOLVED` is a person's decision, not proof the condition ended. Comfort-delta and idle-energy types were not built.

**Tech ID findings** ([TechIdController](../../../cabin-orchestration-platform/backend/src/main/java/com/cabin/orchestrator/techid/TechIdController.java), `/api/tech-id/findings`, shown in the Opportunities panel). A provider submits a finding with the shared key in `X-Tech-Id-Api-Key` (`TECH_ID_API_KEY`; submission answers 503 while it is unset). The provider name is free text, unverified; reading the list is open. A signed-in person sets the status (`new`, `reviewed`, `actioned`, `dismissed`) and logs actions: `see_expand`, `think_include`, `think_dismiss`, `act_purchase_elsewhere`, `act_request_core`, `act_do_it_now`. Each button writes a `tech_id_finding_action` row with the actor; Include and Dismiss also set the status. None of them runs a device command, deploys code or changes a platform setting.

**Answering "was the suggested enhancement implemented?"** Treat the listing, its status, a WSJF score and an old "shipped" plan as a recommendation or a person's decision. Ask for three separate things: the implementing change (PR or commit), the release that carried it (a deployed commit with a green deploy run), and the runtime outcome (for example the condition no longer appearing in telemetry). If one is missing, say which. This guide records no implemented enhancement for any listed opportunity.
