**W-26: Ontology-driven camera object class config** (verbatim from the 2026-10-01 handover)

- **Problem:** Frigate's `track:` list for each camera is maintained by hand in `config.yml`. When the model changes or object classes are added or removed, config drift is likely. The ontology already owns device capabilities, so `CameraNode.monitored_object_classes` (or equivalent) should be the canonical source for what each camera tracks.
- **Proposed resolution:** define `monitored_object_classes` as a property on `CameraNode` in the ontology (ratified list, not auto-generated). At deploy or config-generation time, Frigate's `track:` lists are derived from this property, not hand-edited. An optional drift check (CI step or startup warning) compares live `config.yml` against the ontology values.

## Tooling note: why GitHub posting fails

The GitHub plugin sends `Authorization: Bearer ${GITHUB_PERSONAL_ACCESS_TOKEN}`. That variable is not set at any scope (process, user, machine) on the PC, so the header is empty and GitHub answers 400 "Authorization header is badly formatted". The same error is in Cowork's scratch-workspace MCP logs on 2026-09-16, 09-21 and 09-23. Code is unaffected because it uses the signed-in `gh` CLI. Fix (Nate): set that variable to a GitHub token.
