## 1. P0 write gate (W-31): merged, deployed, verified live

- **PR:** [#115](https://github.com/ImpressiveLLC/FaceoftheCabin/pull/115), merged 2026-10-03 08:23 UTC as `8485b7c`. Allocation commit first (`6e71e3e`, W-31 and W-32 claimed in git before any code), then the fix (`43a045f`).
- **Cause:** `/api/devices/**` was never in `WebConfig`'s interceptor list, so none of its 14 write routes ran any auth code. D14's reversal ungated reads and the writes went with them.
- **Fix:** register `/api/devices/**`, with a GET/HEAD carve-out so reads stay open as D14 decided. Anonymous gets 401; guest and demo tokens get 403; a read-only managed viewer gets 403; household and admin sessions are allowed.
- **Tests:** per route x per credential for all 14 routes, plus the permanent `WriteGateAuditTest` (below). Mutation-checked: with the registration removed it names exactly the 14 unprotected routes. Full backend suite 845/845.
- **Deploy:** [run 37109543361](https://github.com/ImpressiveLLC/FaceoftheCabin/actions/runs/37109543361) success (08:23:35 to 08:27:05 UTC): `mvn test` gate, health check, no rollback. `cabin-backend:8485b7c` healthy, 0 restarts.
- **Live verification (read-only, over Tailscale SSH):** anonymous `POST /api/devices/x/command` returns **401** on the M920q and on `https://api.unicornpingpong.com`. 401 also for `PUT`, `DELETE`, `permit-join`, `network-scan`, `PATCH config`, `lifecycle` and `discovery/run`, and for a bogus `CabinToken` or `CabinSession`. Reads stay open: `GET /api/devices` 200, `HEAD /api/devices` 200, `meta/types` 200, `display-config?profile=AT_CABIN` 200 (the bare `display-config` 400 is its pre-existing required `profile` parameter).
- **Not verified live:** a signed-in write. I have no credential for one. Unit tests cover it, and all 14 UI call sites use `authedFetch`. Someone should click a device command in the UI once.
- **Behavior change:** an anonymous kiosk can still read devices but can no longer issue commands.

### Controller audit

68 write routes found by scanning every `@RestController`. 60 gated and refusing anonymous callers (14 newly), 2 deliberately passed through with their own check (`POST /api/tech-id/findings` shared-secret key, `POST /api/managed-users/magic/{token}/consume` magic-link token), 2 open by design (`POST /api/auth/session/revoke`, `POST /api/webhooks/blink-motion` shared-secret), and **4 open known gap: `/api/locations` POST, PATCH, reorder, DELETE (W-32)**. Actuator exposes only `health,info,metrics`.

**W-32 needs your call.** `/api/locations` writes are anonymous, and the UI builds its API base from the location config and sends signed-in users' tokens there, so an anonymous `PATCH` with an attacker `apiBase` could redirect those credentials. Kept out of the hotfix on purpose: the UI's add-a-place call uses a plain `fetch`, so the gate needs a matching UI change. Proposed score `20+3+4+8 = 35`, size 2, WSJF 17.5 (Code's proposal; Cowork to confirm). Recommend same-day.

`WriteGateAuditTest` now fails the build on any new unprotected write route, and on any stale allowlist entry. When W-32 lands it will force removal of its four known-gap entries.
