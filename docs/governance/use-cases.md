## UC-11 detail

Stated by Nate on 2026-10-04. This section keeps his needs separate from what the code does today, so the first can be scored and the second corrected.

**Relation to other items.** UC-12 (W-27/W-28, merged in #111 on 2026-10-04) covers switching cabin plugs and switches from the dashboard and the "On the Way" button. UC-11 includes that toggle and adds the two things around it: getting to the device from a reading, and seeing and editing its automations. W.6 (concurrent multi-user roles) decides who may do this; until it lands, this use case is for a signed-in administrator or household member under the existing roles.

**What done looks like (observable; drafted by Code from the stated needs, for Nate to confirm).**
1. In Monitoring, selecting a reading opens that device in Device Manager's Change view, scrolled into view.
2. A device that can be switched shows an on/off control; one that supports a level shows a level control within the range its capabilities allow; one that supports neither shows no control and says why. Switching the heater off changes the smart switch's reported state, and the UI says whether the device confirmed it.
3. Valves and locks keep their existing safeguards (UC-12's allowlist excludes them; this use case does not widen that).
4. In both See and Change, a device card lists every workflow that uses the device, each linking to that workflow, with a way to add a new one pre-filled with the device, and edits take effect without leaving the card.
5. Selecting any device shows its details beside or directly below the card, visible without scrolling past the rest of the list, at kiosk width and at phone width.

**Current state, read from code on `main` (`8485b7c`) on 2026-10-04.** Read, not exercised live on the heater's own card.
- **No on/off control for a Zigbee2MQTT-sourced plug.** `DmCapabilityActions` (`ui/src/App.jsx`) offers on and off only when the device's `attributes.entityId` is a `switch.*` or `light.*` Home Assistant entity. `Zigbee2MqttAdapter` sets no `entityId`, so a plug that comes from Zigbee2MQTT (as `heater_mech_room` is documented in `CLAUDE.md`) gets the "this app only offers safe one-tap buttons for a small preset" message instead. The heater has two records. The Home Assistant-sourced one (`ha-cabin-switch-heater-mech-room`) already carried `entityId` `switch.heater_mech_room` and `COMMAND`, so its On and Off buttons existed before #111, in the detail pane at the bottom of the list (need 3). The Zigbee record had none.
- **The toggle was stuck for two days and merged on 2026-10-04; it is deployed.** PR #111 (W-27/W-28, UC-12) maps a device to its `switch.*` entity and calls an allowlisted `POST /api/ha/services`. It sat `CONFLICTING` with `main` from 2026-10-02 with no review, then merged as `1f4e112`. Read-only checks on the M920q, 2026-10-04 evening: `cabin-backend:1f4e112` is running, the served UI bundle contains the new call, an anonymous `POST /api/ha/services` returns 401, and the heater is on and drawing about 785 W. Both heater records (`ha-cabin-switch-heater-mech-room` and `z2m-heater_mech_room`) are `ASSIGNED`, cabin, reporting `ON`, which is what the toggle needs, and the Zigbee one maps to `switch.heater_mech_room`, an entity Home Assistant has. **Not yet confirmed:** the click itself, which needs a signed-in session.
- **Monitoring does not lead to the device.** Monitoring's reading tiles (`KpiTile`) do not navigate anywhere, and Monitoring's own Change view (`MnChangeView`) edits display settings, not the device. The one jump into Device Manager is the "Open device" action on Rules & Alerts' status checks (`StatusChecksCard` sets `pendingDeviceFocus`), and it opens See, not Change.
- **Automations are listed, not reachable.** `DmDeviceWorkflows` shows each workflow that names the device (name and trigger-to-action) and a "Manage in Rules & Alerts" button that opens the panel, not the workflow. There is no "add an automation for this device" and no in-place edit.
- **The detail pane is last in the layout.** `.dm-detail` is the last child of `.dm-layout`: at 900px wide or less it follows the whole device list, and above that it is a 320px right-hand column with no `position: sticky`, so on a long list it sits at the top of the grid while the selected card is far below. `useScrollSelectedIntoView` scrolls the row, not the pane.

**Answered by Nate, 2026-10-04**, to the three questions this section first left open (any current device needing level control, which devices may be switched beyond the heater, what "real time" means). Quoted closely, then read:
- **Not a device list.** Every device that owns services, whether defined by yes/no or by a configurable capability, must be defined and grouped (by class or similar) in the ontology. The UI, automations and other system activity all access, modify and delete through that definition. Level control therefore applies wherever a service is configurable, not to a named device.
- **Who.** Any authenticated user.
- **Overrides and manual activity are first-class.** A manual action either resets after a time-boxed window ("turn off for now") or the user disables it until it is re-enabled.
- **"Real time" was not answered separately.** Cowork to confirm that editing an automation from the device card taking effect immediately is what he means.

**What this changes in the done criteria above.**
- Criterion 2 no longer comes from parsing an `entityId` domain. Controls come from the ontology's service definition for the device's class, so a new device of a known class gets its controls without a code change.
- Criterion 3 needs Nate's confirmation. "All devices" reads as including valves and locks, which UC-12's allowlist excludes ([DL-2026-10-02-02](discrepancy-log.md), "never an id containing `valve` or `lock`"). The proposed reading is that the ontology declares per-class safeguards (for example confirmation, which `action_confirmation_copy` already models) in place of exclusion, so the protection moves from a hardcoded list into the definition. The alternative is to keep the exclusion. This is a safety call, not a default.
- New criterion 6: an override is visible as one (who, when, and either its expiry or "until re-enabled"), and a time-boxed one resets on its own without anyone present.
- New criterion 7: an override and an automation that targets the same device do not fight silently; the card says which is in control.

**Raised by this answer, for Cowork and Nate.**
1. **"Any authenticated user" against W.6.** W.6 (Nate's concurrent multi-user proposal) has non-primary users who can see, think and act but not change CRUD or users without a primary user's authorization. Both are Nate's statements; they need one rule, for example "any signed-in user acts on a device, only a primary-role user edits an automation or a class definition". Not resolved here.
2. **Where the reset timer lives.** `CLAUDE.md` says never duplicate Home Assistant automation logic here. A time-boxed override that resets on its own is automation logic, so the timer most likely belongs in Home Assistant (a timer helper and an automation the platform creates or triggers), with this platform as the control and the record. Needs a feasibility read before any design.
3. **The word "service".** Nate's "services" are a device's capabilities (on/off, level, open/close). In the code, "service" also means a Home Assistant service call (`switch.turn_off`) and, in `device_service_hierarchy`, a device's child entities. The ontology work has to pick one meaning and name the others.
4. **What exists today.** The ontology has ten per-device `action_*` definitions (valve, entry light, deterrent plug, spare siren, water heater switch), each tied to one device and `requires_capability: COMMAND`; a coarse client-side "Workflow" grouping (Alerting, Automations, HVAC, Other); and the `DeviceCapability` enum, which does reach the UI as `attributes.capabilities` (`DeviceRegistry.java`), although an older ontology note says it is never serialized there; that note is stale. There is no class-level declaration of a device's services, which is what this asks for. Tracked as W-45 in `backlog.md`.
