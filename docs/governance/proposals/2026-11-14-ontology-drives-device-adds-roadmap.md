# Ontology drives device adds: roadmap and scope to close the gap

Cowork, Sat 14 Nov 2026, at Nate's direction (21:38 CST). Status: **proposal**. It answers the eight open questions in PR #448 ("Ontology drives device adds: reconciliation of the north star with the code", Code), finds the facts #448 left open, and lays out slices for Code to build. It decides nothing by itself: three real decisions (section 5) go to Nate, and each slice names the decision it waits for. It changes no code, migration, ontology entry, device assignment or gate. Companion records: D27 (ontology-driven context), D28 (Device Type Name registry), the D7 measurement-type parity test, W-84 (ESPHome boxes), W-157 (relocatable devices, `docs/governance/proposals/2026-11-12-relocatable-devices.md`).

## 1. North star and target

Nate's north star (#448 section 1): the ontology drives every device add and every device check-in. Outside the ontology stays only what is specific to one physical unit.

Target in one sentence: **a device is enrolled and checked in against a catalog entry for its type; a device whose type the catalog does not know is held as a candidate and never silently guessed.**

## 2. What is true on main today (facts added to #448, read from code on main at d0079875)

1. **Three type lists, not two.** `DeviceType` (Java enum) carries category and `telemetryFields()`. `docs/ontology.yaml` has the descriptive entities. `App.jsx` `SENSOR_FIELD_OPTIONS` is a third copy of the reported-fields list; the enum's own comment says it "mirrors App.jsx exactly (kept in sync by hand)". The backend already serializes `reportsFields` onto every device read (`DeviceRegistry.withOntologyMetadata()`), so the UI copy can be dropped without new backend work.
2. **Check-in (answers #448 question 6).** `DeviceHealthMonitor` keys on the device id and its last-seen time. The expected window comes from `expectedCheckinMinutes` in the device's attributes when set, otherwise from protocol and power defaults (battery Zigbee 1560 minutes, mains Zigbee 10, HA 15, camera 5, unknown 30). A device is LATE past the window and MISSED past three times it. `GET /api/devices/checkin-status` returns id to status; `GET /api/devices/checkin-details` adds expected minutes, missed-after minutes and a reason. Nothing consults an ontology type. The ontology documents the property (`device_expected_checkin_minutes`, data class `derived`) but does not drive it.
3. **Type inference is a data problem hidden in code.** `HomeAssistantDiscoveryService.inferType` is about 60 lines of rules on HA domain, `device_class`, unit and, in one case, the friendly name, several of them workarounds for vendor gaps (Kidde). These are catalog match rules in all but name.
4. **Part of the catalog already exists as prose.** D28 defines a controlled Device Type Name registry (nine names: SensorCollectionBox, RelayControlBox, UtilityRelayNode, ZigbeeTempHumiditySensor, ZigbeeMiniRelay, ZigbeeSmartPlug, ZigbeeCoordinator, SmartDehumidifier, DuctFanSpeedController) and a mechanical naming rule. `sensor_collection_box`, `sen66_environmental_sensor`, `sht45_ambient_sensor`, `qt_py_sensor_controller` and `zigbee_temperature_humidity_sensor` are ontology entities at `lifecycle_status: candidate`. None of it is read by code.
5. **A drift guard pattern already works.** `D7MeasurementTypesTest` ties a JSON schema to a Java class. `OntologyYamlTest` checks ids are unique and a few named entities exist. Nothing ties device types.
6. **Relocation is already proposed.** W-157 gives identity to the hardware address and derives location from sightings; its entries are `candidate`.
7. **Not verified by Cowork:** #448's live-hub claims about Box 3 (27 live entities, no device row). CLAUDE.md says Doc 27 hardware is "ordered, not commissioned" and W-157 puts Box 2 on a Home bench. Code verifies the state of each box before S7.

## 3. Answers to #448 section 5 (Cowork recommendations; Nate decides where marked)

| # | Question | Recommendation and reason |
|---|---|---|
| 1 | Source of truth direction | **Stage it.** First a parity test (the D7 pattern), then a machine-readable catalog file as the single source with the enum and the UI field list validated against it. Not runtime-decided types: that changes failure modes on the safety path and breaks offline use. Generating Java from the catalog stays a later option once the catalog has soaked. Decision N1. |
| 2 | What a lookup keys on | An ordered match in the catalog: (a) a type the device declares (ESPHome project or device name, Zigbee2MQTT model, HA manufacturer and model), (b) HA domain, `device_class` and unit rules, moved out of `inferType` into catalog `match` entries. The hardware address is identity (W-157), never type. For our own boxes, the firmware declares the type name (W-84 design confirms how). |
| 3 | Unknown devices | **Hold as candidate, flagged "no ontology type", never auto-enabled** for telemetry, workflows, Ask inventory or commands. Today's heuristic becomes a visible suggestion to the admin, not an assignment. Existing assigned devices are grandfathered by giving each a catalog entry first (S4 blocks until none is unmatched). This changes today's behavior, so Decision N2. |
| 4 | What stays outside the ontology | Confirmed list: registry id, hardware address, current location (derived from sightings), the readings. Also per unit: assigned room and application label (the D28 name segments), lifecycle state, install photo, the secret pointer for a box, and an optional check-in override. Type-level facts (category, reported fields, default check-in window, protocol) belong in the catalog. |
| 5 | Runtime dependency | Distinguish **display** from **enroll**. Display keeps today's graceful fallback (humanized id). Enrollment **fails closed** if the catalog cannot be loaded. Ship the catalog in the image, with the bind-mounted copy only as a development override, and expose the catalog hash (it also belongs in the assistant inventory version). |
| 6 | Check-in | Answered in section 2 item 2. Ontology-driven check-in means the catalog holds the default expected window and reported fields per type; the per-device override stays; the check-in payload stays id, readings and hardware address (the type comes from the registry, not from each message). |
| 7 | Telemetry scoping | **Measure first, enforce later.** S6 counts and lists readings a device sends that its type does not declare, with no drops. An undeclared reading is never deleted (repository storage rules protect BI telemetry); if enforcement is chosen later, undeclared readings go to a quarantine metric. |
| 8 | Sequencing with W-84 and relocatable devices | Box enrollment does not wait for the whole path, but it should be the **first catalog-native add** (S7), because W-84 already needs catalog entries for the D28 types. W-157 runtime stays its own gated slice after S3. For Box 3's metrics today, see Decision N3. |

## 5. Decisions for Nate (the only three)

**Status (added 2026-11-15):** Nate's rulings on N1 to N3 were relayed by Code on #244 (comment 6889276499, "recording Nate's rulings from chat"). They are recorded below as **ruled, relayed by Code; Nate's direct confirmation to Cowork pending**. S0 turns them into a D-id (next free id at PR time) only after that confirmation. S1 is merged (PR #450, 84af1583).

- **N1. Direction: ruled (staged, catalog file), with Nate's amendment.** Nate's words, as relayed: the catalog file is organized and driven by the ontology; every ontology change can potentially change the catalog; governance must prevent unvalidated change with a brake that works as a circular loop. When the ontology is checked in or modified, any change that would affect the catalog must be tested and validated before the changing party may save the ontology. Every catalog entry then validates that the newest ontology is loaded; if not, it pulls the newest and overlays it onto the catalog, in effect driving add, amend, append and delete at field level or row and column level. Code's reading (to be confirmed by Nate): (a) the ontology drives the catalog, one direction; (b) a pre-save gate on ontology changes that affect the catalog; (c) each catalog entry records the ontology version it was built from and is checked against the current one, a stale entry is refreshed and the change applied at field or row level. **Refresh timing: ruled (as relayed by Code, #244 comment 6889494027): build and review time**, a generated change committed through a PR, with a version check kept in. Nate's added requirements (Code's reading): (1) at adjudication the ontology version a device was matched against must equal the ontology version in the run tables, and a mismatch refuses enrollment; (2) the same check over all devices as a gate that may sit in git or CI; (3) periodic new-device detection in regressions or other tests; (4) self-healing on a numbering or registry conflict, a bad insert or a UI overwrite: assign a temporary id, test, restore the last known good, which traces back to the ontology. Code found (1) to (4) are new: only the re-detect rollback (W-93) and canonical id repair plans (W-101, W-101b) exist, with no ontology version on device rows. S2 is unblocked: the catalog is generated from the ontology (Nate's call on hand-edits vs a generator script stays Code's design note in S2). Cowork note (proposed): D27 R-OC-1 (one runtime store, `docs/ontology.yaml` reconciled to it) and W-68 (proposed, not built) overlap this; the W-68 design note should name the catalog as its Phase 1 seed so there is one source, not two.
- **N2. Unknown devices: ruled (as relayed).** An unmatched device is a flagged candidate and is never auto-enabled: no telemetry, workflows, Ask inventory or commands until matched. The heuristic becomes a visible suggestion. Existing assigned devices are grandfathered. Added requirement (Code's recommendation, adopted into S4): the status board shows a count of unmatched devices.
- **N3. Box 3 meanwhile: ruled (as relayed), wait for S7.** No interim assignment. Box 3's platform metrics stay unrecorded until S7 and the W-84 gate; live values remain in Home Assistant.

## 6. Risks

1. **Two sources of truth between S2 and S4.** The parity test is the control; S3 is shadow only.
2. **Misclassifying a safety device** (leak, valve, lock, CO). S4's acceptance names them; S3's disagreement report is reviewed by Codex before S4 starts.
3. **Packaging.** A catalog that depends on the bind mount repeats today's gap; the image copy fixes it, and enrollment fails closed.
4. **Grandfathering.** The 13 Zigbee devices and the HA-discovered entities must all match before S4 ships.
5. **Hardware state is unverified.** Box commissioning status differs between CLAUDE.md, W-157 and #448; Code verifies before S7.

## 7. Out of scope

Relocatable runtime (W-157), the W-84 firmware, ontology semantic expansion, Ask routing, any device command path, and any deploy. Omission is not permission.
