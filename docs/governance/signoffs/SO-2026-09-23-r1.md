### 3.2 Requirement R-GD — guest denial contract (UC-5)

Every guest-token denial returns one shape from one shared handler.

| Situation | HTTP | `code` | Viewer sees |
|---|---|---|---|
| Valid token; route outside its scope | 403 | `GUEST_SCOPE_NOT_INCLUDED` | Neutral info panel; rest of page keeps working |
| Valid token; any non-GET method | 403 | `GUEST_READ_ONLY` | Neutral info panel, view-only wording |
| Token expired, revoked or unknown | 401 | `GUEST_LINK_INACTIVE` | Full-page notice |
| Server error on an allowed route | 5xx | unchanged | Normal error state; never the denial panel |

Body for the three denial codes:

```json
{
  "code": "GUEST_SCOPE_NOT_INCLUDED",
  "denied_by_design": true,
  "message": "This area is limited to signed-in household members.",
  "scope_held": ["dashboard", "device_states", "alerts_read", "observations_read"]
}
```

The body must not name the required scope or any route map.

UI copy, exact:

- Scope: "Not included in this view. This part of the cabin dashboard is available only to signed-in household members. Everything shared with you is shown on this page."
- Read-only: "This is a view-only link. Changes can only be made by signed-in household members."
- Inactive: "This link is no longer active. Access links are time-limited by design. Contact the person who shared it if you still need access."

UI rules: out-of-scope panels are not rendered; the denial panel is neutral (lock icon, no red, no "Error", no retry); denials log at INFO under a dedicated event type with token id, route and code, excluded from error alerting.

Required tests: all three codes on the routes listed in W-2; and a forced 5xx on an allowed route must not return `denied_by_design`.
